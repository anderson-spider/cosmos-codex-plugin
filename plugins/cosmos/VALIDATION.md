## Git Master

- The public skill covers inspection, preparation, commit, push, PR/MR, and CI for GitHub and GitLab through progressively loaded references.
- Commit requires a request to commit or publish. Push, PR/MR mutation, and CI retry, rerun, or cancellation remain independent authorizations.
- Merge, approval, auto-merge, tags, releases, branch deletion, and force-push are explicitly outside the contract.
- The internal `cosmos-git-master` profile recommends **gpt-5.6-terra / medium** and is not registered automatically in the `@` selector.
- A local scan of new content found no private names, domains, or accounts from the source skills. Identifiers were not recorded as fixtures or rules in the public repository.
- Installed discovery and execution of `$cosmos:git-master` still depend on a future release, reinstallation, and a new session; this delivery does not remove local skills used as fallback.

## Reproduce authoring validators

With the plugin-creator and skill-creator system skills available, run `validate_plugin.py <plugin-folder>` and `quick_validate.py` for `skills/cosmos-orchestrate` and `skills/git-master`.

Demo files are provided separately in `../../demo-cosmos/`. From this directory, run `python3 -m unittest discover -s ../../demo-cosmos -v`. The demo is synthetic, uses only the Python standard library, and does not access production.

Activation through `@Cosmos` and automatic discovery still need verification after reinstalling this version and starting a new app conversation. Automated validation confirms the package contract but does not replace that end-to-end observation.

## Activation matrix

Automated tests verify that starter prompts invoke installed skills by namespace and that metadata does not disable automatic discovery. After reinstallation, app evaluation should record:

- `@Cosmos` followed by a small task: Cosmos active and direct execution declared.
- `$cosmos:cosmos-orchestrate` followed by a complex task: Cosmos active and observable delegation when beneficial.
- A textual mention of the Cosmos workflow: automatic skill discovery.
- An ordinary development or subagent request without Cosmos: the skill must not be selected based only on those terms.
- Continuation of the activated request: the workflow remains active.
- An out-of-scope request: no activation or unsupported action.
- `$cosmos:git-master` followed by a preparation request: no local or remote mutation without corresponding authorization.
- An ordinary Git, PR/MR, or CI request: automatic Git Master discovery when applicable.
- Delegation of a substantial Git workflow by the Orchestrator: `cosmos-git-master` profile, sibling skill loaded, and authorization boundaries preserved.

## Executed demonstration

The conversation's primary agent acted as Orchestrator with `gpt-5.6-sol / low`, fresh context, and the skill as input; no registered Orchestrator profile was used. It created Explorer (`gpt-5.6-luna / medium`), Executor (`gpt-5.6-terra / medium`), and a new Executor for independent review (`gpt-5.6-terra / medium`) sequentially. Models and effort levels were passed explicitly to native calls. Oracle, Librarian, and Designer were not used.

Request: fix a JSON configuration merge function. Explorer identified shallow merging, discarded falsy values, and shared mutable structures. Executor changed only the function and its tests. The reviewer found no material defects and checked additional in-memory cases. The original test passes even with the defective code; the expanded suite covers the requested behavior.

Result: **5 tests passed**, covering basic overrides, recursive merge and preservation, falsy values and `None`, list replacement, and structure isolation from both inputs. The previous function was preserved in `settings.before.txt` for comparison. The three-stage flow was explicitly requested for demonstration; for a request of this size, the skill's default behavior would be direct execution. No model or delegation failure occurred.

## Independent static skill review

Executor/Terra medium assessed agent selection and the cases of small requests, missing tools, unavailable models, concurrent edits, and effort escalation. It found an incomplete condition in profile selection by name. The skill was corrected to also require that the tool expose that selector; tools like the one in this session use generic creation. These situations were analyzed statically, not run as end-to-end tests.

Regression control: the expanded suite was run in memory against the previous function; **2 tests failed and 1 ended with `KeyError`** because the shallow merge discarded a required key. All 5 tests pass with the corrected version.

A real report showed the Orchestrator saying that Cosmos "did not expose an actionable skill or tool" while `cosmos-orchestrate` was already loaded. The contract now separates three states: active skill, decision to execute directly, and unavailable native delegation. Static review confirmed that only the third state should be reported as a limitation; direct execution remains Cosmos behavior.

## Versioning and Conventional Commits

The repository uses Semantic Release to calculate versions, notes, and tags,
with Commitlint in CI for commits and PR titles. The release workflow is manual.
During `prepare`, the package and source manifest receive the calculated version;
`@semantic-release/git` commits the manifest before tag creation.

Local validations after adding Git Master passed: `npm test` (21 tests),
`python3 -m unittest discover -s demo-cosmos -v` (5 tests), `git diff --check`,
and all three authoring validators. All six TOML profiles also loaded through
`tomllib`. The release configuration loaded earlier also confirmed the order
`prepare-release` → `@semantic-release/git` → `@semantic-release/github`.
`actionlint` is not installed in this worktree.

In the previous release-workflow validation, the sample package
`cosmos-1.0.0.zip` was generated, extracted to a temporary directory, and passed
the plugin and skill validators. That package is a local simulation, not a
published release.

Commit integration tests use the real analyzer and Commitlint libraries. Package
tests use temporary repositories without publishing to GitHub. Full publication
with `GITHUB_TOKEN` depends on branch permissions and can only be proven by a
manual run after merge.
